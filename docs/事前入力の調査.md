# 事前入力（prefill）の調査記録

同じ仮説を二度検討しないための記録。**外部の挙動についての主張は、必ずここに
「確認済み / 未確認 / 反証済み」のどれかで残す。**

---

## 決着（2026-08-25）：原因は選択肢の文字列を潰していたこと

**「1〜3番までしか入らない」の原因は、キャッシュでも引用符でもURL長でもなく、こちらのバグだった。**

`probe.js` が選択肢を読むときに `label.replace(/\s+/g, ' ')` をしていた。
JS の `\s` は**全角スペース（U+3000）にも改行なし空白（U+00A0）にもマッチする**ので、
`form-map.json` に潰れた文字列が保存されていた。

```
実物: 1.[U+3000]学傷補のみ加入[U+00A0][半角]Register only for “Compensation for Injury”
保存: 1.[半角]学傷補のみ加入[半角]Register only for “Compensation for Injury”
```

事前入力は完全一致が要るので、**選択肢は一つも一致しなかった**。
テキスト設問は利用者の入力値をそのまま送るので無傷 → だから毎回きっちり1〜3番。
5番（ラジオ）が入らないので段階表示が開かず、6番以降は画面にすら出なかった。

### 実機で確定したこと

| # | 事実 | 根拠 |
|---|---|---|
| G1 | 選択肢の事前入力は**効く** | 4番で「いま選ばれていない方」を送り、選択が切り替わることを確認 |
| G2 | **引用符はあってもなくても効く** | 同じ選択肢を引用符あり／なしで送り、どちらも効いた |
| G3 | 正本は `input[type=radio]` の **`value` 属性** | 実機の HTML で確認。`aria-label` は空で、文字は隣の span にある |
| G4 | ドロップダウンの `[role=option]` には value 属性が**無い** | 生の `textContent` を使う |
| G5 | 5番の選択肢7件は**すべて NBSP 区切り** | `1.授業[U+00A0]Class`。半角スペースではない |
| G6 | 36択のうち2件も特殊な空白を含む | 所沢…は U+3000、アントレプレナー…は U+00A0 |

**選択肢が入らないときに疑うのは、書式ではなく文字列の一致。**

### 設問は条件で16〜18問に増減し、表示番号は振り直される

| | 8/24 | 8/25 |
|---|---|---|
| 6.参加者は全員科目登録者ですか（授業のときだけ） | 出ていない | 出ている |
| 【その他の場合のみ】箇所名（その他のときだけ） | 出ている | 出ていない |

17問だったのは偶然。`expectedCount: 17` の決め打ちのせいで、
正常な状態でも「大学がフォームを変更した」と**嘘の警告**が出ていた。いまは 16〜18 の範囲で見る。

**設問IDは変わらない。** だから照合は設問ID優先で、並び順には頼らない。

### 8/24 の調査データが歪んでいた理由

当時の probe はドロップダウンを開いて閉じ損ね、**活動主管箇所名を「その他」に変えてしまった**。
その状態のフォームから form-map を作ったので、設問構成の解釈まで狂った。
さらに「事前入力テスト」機能が ZZ 値を実際に書き込み、下書きを汚していた。
**この2段階テストは 2026-08-25 に削除した。調査ツールは読むだけにする。**

### 再発防止

- `verify-choices.mjs` — 選択肢に U+3000 と U+00A0 が**残っていること**を検査。潰した瞬間に落ちる

## 訂正（2026-08-25・その2）：URLを膨らませていたのはハッシュだった

前節で「事前入力クエリが長いから撤去する」と書いたが、**これは測らずに決めつけた誤り**。
`AADSTS90015` は**サインイン済みのブラウザで**起きており、「未サインインだから」という
説明も成り立たない。

内訳を実測したらこうだった。

| リンクの内訳（エラーが出た版） | 文字数 |
|---|---|
| ベース（`?id=…`） | 145 |
| 事前入力クエリ | 1,292 |
| **ハッシュ（`#gsh=…`）** | **5,652 ← 全体の80%** |
| **合計** | **7,089** |

**膨らませていたのはハッシュ**（ブックマークレットに値を渡す仕組み）だった。
それなのに私は、利用者が求めている事前入力を削り、原因のハッシュを残した。**完全に逆。**

### いまの形

- リンク = **事前入力クエリのみ**（ハッシュは載せない）→ **1,437文字**
- ブックマークレットへは、リンクを押したときに**クリップボード**で値を渡す
- まだ長い場合に備えて「URLを短くする」を用意。**分岐を開く設問（5番・8番）と選択肢は
  絶対に外さず**、長い自由記述から外す（1,005文字・11問）

`verify-browser.mjs` が実際に生成されたリンクを測り、ハッシュが載っていないこと・
長さが実用域であること・選択肢が引用符付きであることを毎回検査する。

**教訓：長さの問題は、決めつける前に内訳を測る。** 4倍大きいほうを見逃していた。

## 旧・結論（2026-08-25・撤回済み）：事前入力は使わない

書式を直したうえで**未サインイン状態**で開いたところ、Azure AD がサインインごと拒否した。

```
AADSTS90015: Requested query string is too long.
```

未サインインだと Forms は `login.microsoftonline.com` へリダイレクトし、
**元の URL 全体が認証リクエストに埋め込まれる**。事前入力クエリは1,300文字を超えるので、
エンコードされて Azure AD の上限（概ね2,048文字）を突破する。

**v1.3.0 で新しく壊れたのではない。** 事前入力クエリは v1.1.0 からずっと長く、
これまではサインイン済みのタブで試していたのでリダイレクトが起きず、顕在化しなかっただけ。
**最初から地雷だった。**

### 3つ揃って、リンク単体では成立しないと確定

| 分かったこと | 影響 |
|---|---|
| 値の書式が種別ごとに違う | 直せる |
| フォームが段階表示（5番→6〜8番、8番→以降） | 5番が入れば開くかもしれない（未検証） |
| **長い URL は未サインイン時にサインインを壊す** | **致命的** |

短くするには載せる設問を減らすしかないが、それはブックマークレットが全部やるので意味がない。
**「フォームを開く」リンクは素のフォームURL＋ハッシュだけ**にして、15問はブックマークレットが埋める。

- サーバに送られるのは **91文字**（実測）→ 認証リダイレクトが太らない
- ハッシュはサーバに送られないので長さは認証と無関係
- サインインのリダイレクトでハッシュが失われる場合に備え、同じ値をクリップボードにも置く

`verify-browser.mjs` が**実際に生成されたリンクを測って**、クエリ部が300文字未満であることを
毎回検査する。わざと事前入力を戻すと落ちることも確認済み（924文字 → NG）。

`src/core/prefill.js` は使っていないが、**値の書式は調べ直したくない知識**なので
モジュールとテストごと残してある。

## 原因の確定（2026-08-25）

**2つの要因が重なっていた。**

### 要因1：値の書式が種別ごとに違う

事前入力の値は、設問の種別によって書き方が違う。私は**全部を裸のテキストで送っていた**。

| 種別 | 正しい書式 | 例（エンコード前） |
|---|---|---|
| 単一行/複数行テキスト | そのまま | `?rXXXX=山田太郎` |
| **選択肢（ラジオ・ドロップダウン）** | **ダブルクォートで囲む** | `?rXXXX="1.国内 Domestic"` |
| **日付** | **yyyy-MM-dd をダブルクォートで囲む** | `?rXXXX="2026-09-01"` |
| 評価・NPS | 数値そのまま | `?rXXXX=3` |

出典: <https://qiita.com/Rinatamu/items/f583444932cc2382e6bb>（利用者から提供）

### 要因2：フォームが段階表示（分岐）になっている

| 段階 | 見えている設問 | 開く条件 |
|---|---|---|
| 初期 | 1〜5 | — |
| 次 | 6, 7, 8 | 5番（活動の種類・ラジオ）に回答 |
| 次 | 〜16 | 8番（活動主管箇所名・ドロップダウン）に回答 |

### 2つが重なるとどうなるか

1. 1〜3番（テキスト）は書式が合っていたので**入った**
2. 4番（ラジオ）は引用符が無いので**入らない**
3. 5番（ラジオ）も**入らない** → **分岐が開かない**
4. 6番以降はそもそも画面に存在しない → **何をどう送っても届かない**

**観測がすべて説明できる。** URL の長さも並び順も綴りも、最初から無関係だった。

## やり方についての反省

この件では**仮説 → 修正を出す → 試してもらう → 外れる、を3回繰り返した。**
原因は次の4つ。同じことを繰り返さないための決めごとにする。

1. **利用者をテスト装置にしていた。** 1往復で1つの仮説しか潰せない設計だった。
   → **切り分け用の実験は、複数の仮説を一度に潰せる形でまとめて渡す。**
2. **実験を制御していなかった。** 同じブラウザ・同じプロファイルで連続して試したため、
   キャッシュ・下書き・前回の状態が混ざった。
   → **1テストにつき新しい InPrivate ウィンドウ。1テストで1変数だけ動かす。**
3. **観測を目視に頼っていた。** 「何番まで入ったか」を人間に数えさせていた。
   → **読み取りブックマークレットで機械的に取る。**
4. **未検証のものを既定の導線にした。** v1.2.0 で事前入力を主導線に格上げし、
   検証済みのブックマークレットを格下げした。しかも画面に「15項目が入ります」と**嘘を表示した**。
   → **確認できていないことは断定しない。既定の導線は必ず検証済みのものにする。**
5. **相手の仕様を調べる前に、自分の送り方を疑い続けた。**
   決着したのは、利用者からの「5を入力しないと以降が出てこない」という一言と、
   利用者が見つけた記事（値の書式）だった。**こちらが3往復かけて潰した仮説は
   すべて的外れ**で、当たったのは「相手はどうなっているか」という情報だった。
   → **手元で読めない相手を扱うときは、まず相手の仕様と画面の構造を調べる。**
      自分のコードを疑うのはその後。
6. **模擬フォームが実物と違っていた。** 段階表示を再現していなかったので、
   `verify-filler` の「15/15通った」は**実物と違う相手に対する検証**だった。
   実際、段階表示を再現した途端に9問が埋まらないバグ（固定待ちへの依存）が出た。
   → **模擬は実物の分かっている性質をすべて再現する。**
      再現していない性質があるなら、そこは「検証済み」と言わない。

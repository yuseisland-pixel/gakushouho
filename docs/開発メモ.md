## 1. 名簿テンプレ（xlsx）の内部構造

`src/template/参加者名簿.xlsx`。大学配布物。**手で編集しないこと。**

### シート構成

シートは「参加者名簿」1枚のみ。`dimension` は `A1:H60`。

| 場所 | 内容 |
|---|---|
| `B1`（B1:C1 結合） | 申請者氏名の記入欄 |
| `B2`（B2:C2 結合） | 科目名/行事名/活動名の記入欄 |
| `B3`（B3:C3 結合） | 責任者名の記入欄 |
| `G1` | 「書式更新日：2026/3/23」← テンプレ改訂の検知に使える |
| 行5〜8 | 注意書き |
| 行9 | 各列の入力ルール |
| 行10 | ヘッダ `No / 学籍番号 / カナ氏名 / 申請年月日 / 活動開始日 / 活動終了日 / 活動場所 / status` |
| 行11〜60 | データ50行。Excel テーブル `テーブル1` が `A10:H60` |

### 書き込むセルのスタイルと値の型

`xl/styles.xml` の `cellXfs` を実際に読んで確認した対応。**ここを間違えると壊れる。**

| 列 | style | numFmtId | 書く値 |
|---|---|---|---|
| B 学籍番号 | `s="3"` | 49（`@` 文字列） | インライン文字列 |
| C カナ氏名 | `s="4"` | 0 | インライン文字列 |
| D/E/F 日付 | `s="5"` | **14（日付）** | **Excel シリアル値（数値）** |
| G 活動場所 | `s="19"` | 49（文字列） | インライン文字列 |
| B1/B2/B3 | `s="30"` | 0 | インライン文字列 |

日付列は日付書式なので、`"2026/9/1"` という**文字列**を入れてはいけない。
左寄せの文字列として入り、大学側が日付として扱っていた場合に壊れる。
シリアル値は 1899-12-30 起点（`date1904` 属性なし = 1900年系）。
`Date.UTC` で計算すること（ローカル時刻で計算するとタイムゾーンで1日ズレる）。

### 落とし穴：H列 status のキャッシュ値

`H11:H60` は数式列 `IF(OR(各必須列=""),"F","T")` だが、**キャッシュ値が全行 `<v>F</v>` で保存されている。**

セル値だけ書き換えると、Excel で開くまでは status が F のまま。
大学側が openpyxl の `data_only=True` などでキャッシュ値を読んでいた場合、
**全行「不備」と判定される。** 対策は2つ両方やる:

1. 埋めた行のキャッシュ値を自前で `T` に書き換える
2. `xl/workbook.xml` の `<calcPr>` に `fullCalcOnLoad="1"` を足す

あわせて `xl/calcChain.xml` は削除する（Excel が開くときに作り直す）。

### 落とし穴：A列 No は数式ではない

`xl/tables/table1.xml` の `calculatedColumnFormula` には
`IF(OR(...),"",ROW()-8)` が定義されているが、**シート実体の `A11:A60` は静的な数値 1〜50**。
`calcChain.xml` にも A列は載っていない（H列の50セルのみ）。

つまり A列は触らなくてよい。逆に、**汎用の xlsx ライブラリでテーブルを再生成すると
A列が数式に戻り、原本と挙動が変わってしまう。**

### その他

- データ検証: `B11:B60` は文字数 = 8 かつ IME 無効、`C11:C60` は IME 全角カナ
- `<sheetProtection insertRows="0" deleteRows="0"/>` は `sheet="1"` 属性がないので**保護は無効**。
  解除処理は不要
- 書き込み先セルはすべて自己閉じタグ（`<c r="B11" s="3"/>`）で、行・スタイル・spans は完備。
  **行追加もスタイル生成も不要で、1タグの置換だけで書き込みが終わる**
- インライン文字列（`t="inlineStr"`）を使えば `sharedStrings.xml` を一切触らずに済む

### なぜ zip を直接パッチしているのか

`customXml/item1.xml`（14KB）は **SharePoint のコンテンツタイプ定義**、
`customXml/item2.xml` には **`_Flow_SignoffStatus`** というプロパティがある。
`docProps/custom.xml` の `ContentTypeId` も同じ紐付け。

つまりこのテンプレは大学の SharePoint 上にあり、**提出された名簿を Power Automate の
フローが自動処理している**とみてよい。「壊さない」は見た目の問題ではなく、
大学側の処理が通るかどうかの問題。

主要ライブラリの適性を調べた結果:

| 方式 | テーブル | 数式 | データ検証 | customXml |
|---|---|---|---|---|
| SheetJS Community | ✕ | △ | ✕ | ✕ |
| ExcelJS | △ | △ | ○ | ✕ |
| **zip 直パッチ** | **保持** | **保持** | **保持** | **保持** |

通常 zip 直パッチは危険だが、このテンプレは条件が良い（書き込み先セルが既に存在、
行追加なし、sharedStrings を触らない）ので、**むしろ最も壊れにくい**。
`xl/worksheets/sheet1.xml` と `xl/workbook.xml` の2つだけ差し替え、
残り20エントリは**圧縮済みのバイト列をそのままコピー**する。

zip の展開・圧縮はブラウザ標準の `DecompressionStream` / `CompressionStream`（`deflate-raw`）を
使うので、外部ライブラリはゼロ。CRC32 だけ自前実装（`src/core/zip.js`）。

## 2. Microsoft Forms 側

### リダイレクト先（実測）

```
https://forms.office.com/r/CpCUfPQRA6
  → 301 → https://forms.office.com/pages/responsepage.aspx?id=<ID>&route=shorturl
  → 301 → https://forms.cloud.microsoft/pages/responsepage.aspx?id=<ID>&route=shorturl
```

**最終的なホストは `forms.cloud.microsoft`**（新ドメインへ移行済み）。
ユーザースクリプトや拡張を作る場合、`@match` / `host_permissions` に
**`forms.office.com` と `forms.cloud.microsoft` の両方**を入れること。片方だけだと動かない。

### CSP（実測、2026-08-24）

```
object-src 'none';
script-src 'nonce-…' 'unsafe-inline' 'unsafe-eval' 'strict-dynamic' https:;
base-uri 'none';
require-trusted-types-for 'script';
report-uri https://csp.microsoft.com/report/Forms-PROD
```

ここから決まること:

1. **`'strict-dynamic'` があるので、`https:` と `'unsafe-inline'` は無視される。**
   nonce を持たない `<script src="https://cdn...">` の注入は**必ず失敗する**。
   → ブックマークレットは自己完結でなければならない（CDN からライブラリを読めない）。
2. **`require-trusted-types-for 'script'` があるので、`innerHTML` への代入は TypeError で落ちる。**
   → フォーム上で動くコード（`probe.js` / `filler.js`）の UI は
   `createElement` / `textContent` / `appendChild` だけで組むこと。
   `tools/verify-bundle.mjs` がこれを機械的にチェックしている。
3. `connect-src` / `default-src` の指定はないので `fetch()` は自由。
4. ブックマークレットの `javascript:` URL 自体は CSP の対象外（ブラウザ仕様）。
   既存ブックマークレットが動いている実績が裏付け。

### フォーム ID の構造

URL の `id=` パラメータは base64url。**全体を復号してから 16 バイトずつ切る**と
テナント GUID とグループ GUID が取れる（base64 文字列を22文字ずつ切るのは間違い。桁がズレる）。

```
id 全体 (88文字) → 復号 66 バイト
  bytes[0:16]  → テナント GUID  b3865172-9887-4b3a-89ff-95a35b92f4c3（早稲田）
  bytes[16:32] → グループ GUID  01a0cccb-1d28-46b0-88df-b3c0f797a8be
  bytes[32:]   → フォーム固有部分
```

GUID の復元はリトルエンディアン（最初の3ブロックはバイト順を反転する）。

#### 既存ブックマークレットが誤った欄に入力していた（重要）

大学が **9番の条件付き設問を後から追加した**ため、それ以降の設問が1つずつズレた。
既存ブックマークレットは設問をインデックスで指定していたので、

- `q[8]`（責任者名のつもり）→ 実際は **9.【その他の場合のみ】箇所名**
- `q[12]`（国内/海外のつもり）→ 実際は **13.参加学生数**（テキスト欄なのでクリック対象が無く、静かに素通り）

つまり **10.責任者名 が空**、**9.箇所名 に責任者名が誤入力**、**14.国内/海外 が未選択** の状態で提出されていた。
9番を取り除いた16問の並びで検算すると両方とも正しく当たるので、この説明で確定とみてよい。

**設問IDは設問を作り直さない限り変わらない**ので、ID で引けばこの壊れ方はしない。
`tools/verify-probe.mjs` の `[6]` がこのバグそのものを回帰テストにしている
（設問を1つ挿入した模擬フォームで、インデックスはズレるが設問IDは不変であることを確認）。

#### 事故の記録：プローブが本番フォームの回答を書き換えた（2026-08-24）

「読み取るだけ」と説明して配ったプローブが、**本番フォームの 8.活動主管箇所名 に
「その他 Other」を選択させてしまった**。日付ピッカーも2つ開いたまま残した。
送信前だったので大学側には届いていないが、起こしてはいけない事故だった。

原因は3つ重なっている。

1. **日付欄をドロップダウンと誤判定した。** Forms の日付設問は `<input role="combobox">`。
   `[role="combobox"]` で拾っていたので、日付ピッカーに対して「開く」処理が走った。
2. **開いたものを閉じられていなかった。** `closedAfter: false`。Fluent のコンボボックスは
   **開いたままフォーカスが外れると活性項目を確定する**。実際に選ばれたのは末尾の「その他 Other」。
3. **「読み取りのみ」をテストしていなかった。** 選択肢が取れたことしか見ておらず、
   回答状態が変化していないことを assert していなかった。

対策:

- **ドロップダウンを開く処理は既定で無効**（`window.GSH_PROBE_OPEN_DROPDOWN = true` で明示的に有効化）。
  36件の選択肢は採取済みなので、通常は開く必要がない
- 日付欄を `dropdown` より先に `date` として判定する
- 閉じるときは **Escape → blur → 外側クリック** の順で、`aria-expanded` を見て確認する
- 開く前の表示を控え、閉じた後に一致しなければ**出力の先頭に警告を立てる**
- **模擬フォームに「開いたまま blur すると末尾の項目が確定する」挙動を再現**し、
  probe 実行の前後で全設問の回答状態をスナップショット比較する

さらに `verify-probe.mjs` の `[4c]` で、**Escape の送出を取り除いた壊れた版を走らせて
副作用検査が実際に落ちること**を毎回確かめている。これがないと「OK」が形骸化する
（実際、壊した版では `選択してください → その他 Other` という本番と同じ症状が再現する）。

#### 設問IDの採取で気をつけること

設問要素に `id="QuestionId_r<32桁hex>"` が付く。ただし**ドロップダウンのトリガには
`QuestionId_xxx-trigger` のような派生IDが付く**ので、単に「配下で最初に見つかった id」を
拾うと別物を掴む。`^QuestionId_(r[0-9a-f]{32})$` に完全一致するものだけを認め、
**要素自身の id を最優先**すること（`src/form/probe.js` の `idsOf`）。

#### 実測で確定した仕様（2026-08-24）

- **日付書式は `yyyy/MM/dd`。** placeholder が `日付を入力してください(yyyy/MM/dd)` と明示。`lang="ja"`
- **13.参加学生数は数値のみ**（placeholder が `値は数値にする必要があります`）
- **テキスト欄の maxlength はすべて 4000**
- **必須設問は1つもない**（全17問 `required: false`）。空でも送信できるので、こちら側の入力漏れチェックが重要
- 設問IDは questionItem 自身ではなく**子孫の div** に付く（`qidFrom: "descendant"`）
- **本物の formapi のパスは `forms('{id}')`**。こちらが 401 になったのは
  `light/runtimeForms('{id}')` という存在しないパスを組み立てていたから。
  ページ自身は `.../groups/{group}/forms('{id}')/localeResource/'ja'` を叩いている。
  ただし DOM から全部取れるので当面この API は不要
- ページ埋め込みの設問定義はなし

#### ドロップダウン（8.活動主管箇所名）

Fluent UI の Dropdown で、**閉じている間は選択肢が DOM に存在しない**。開くと
**選択肢リストが `document.body` 直下にポータルされる**ので、設問ノードの内側を探しても見つからない。

これで、既存ブックマークレットの `clickOpt(q[7],'学生生活課')` が**何もしていなかった**であろうことも説明が付く
（閉じたドロップダウン内にあるのはプレースホルダだけ）。8番が必須設問なら手で選んでいたはず。

### 設問一覧の取得

ページ自身が使っている読み取り API:

```
https://forms.cloud.microsoft/formapi/api/{tenantId}/groups/{groupId}
  /light/runtimeForms('{id}')?$expand=questions($expand=choices)
```

**ログイン済みブラウザから `fetch(url, {credentials:'include'})`** で叩ける。
匿名だと `{"error":{"code":"701","message":"Required user login."}}` が返る。

`src/form/probe.js` がこれをやる。取れれば設問 ID・見出し・型・選択肢が全部手に入り、
**設問の並び順に一切依存しないマッピング**が作れる。失敗しても DOM 走査にフォールバックする。

### 事前入力リンク（prefill）

事前入力リンクの正体は `…responsepage.aspx?id=<フォームID>&r<設問ID>=<値>` という
**素のクエリ文字列**で、署名やトークンを含まない。

つまり**フォーム所有者（学生生活課）でなくても、設問 ID さえ分かれば組み立てられる。**
「事前入力リンクは所有者しか作れない」というのは Forms の UI 上の話であって、
仕組みの制約ではない。

DOM 注入に対する利点:
- 設問の並び順に依存しない
- 遅延描画対策のスクロール往復も、React の value setter ハックも不要
- ブックマークレットの登録という、非エンジニアが一番つまずく手順が消える

制約:
- **ファイルアップロード設問は事前入力できない**（名簿は必ず手で添付）
- 選択肢は表示テキストの完全一致が必要
- URL が長くなりすぎる項目は落とす必要がある（`src/core/prefill.js` が自動で落とす）

**まだ実測していない。** 調査ブックマークレット v2 が「事前入力テストへ進む」ボタンを出すので、
それを押して遷移した先でもう一度実行すれば、何がどう入ったかが自動で読み戻される。

#### 実装で踏んだバグ2件（回帰テスト済み）

1. **設問IDに `r` を二重付与していた。** 設問IDは `r829848…` のように **`r` を含んだ全体**が ID。
   `'r' + qid` としていたため `rr829848…` という存在しないパラメータ名になり、事前入力が丸ごと無反応になる。
   なお「さらに `r` を前置する」流儀の情報もあるため、`prefixMode` で切り替えられるようにし、
   `'both'` で両方の綴りを同時に送って実測で確定できるようにしてある。
2. **`URLSearchParams.toString()` が空白を `+` にしていた。** 選択肢は完全一致が要るので、
   `1.国内 Domestic` が `1.国内+Domestic` になると一致しない。クエリは手組みし、
   値は `encodeURIComponent`（空白は `%20`）で作ること。

どちらも `tools/verify-bundle.mjs` の「事前入力 URL の組み立て」で機械的に検査している。

#### 事前入力は「効く」。ただし設問順に穴を空けてはいけない（2026-08-25 確定）

実機の観測はこの2つ。

| 送り方 | 結果 |
|---|---|
| 設問順に並べたが4番だけURL長で脱落 | **1,2,3 が入り、4番の手前で停止** |
| 1,5,11,13 と飛び飛び（素のID／r前置とも） | **1問も入らない** |

この2つを1つで説明できるのが「**Forms は設問順に処理し、URL に無い設問に当たった時点で
以降を捨てる**」。1番の次に5番が来た時点で打ち切られたので、飛び飛びだと全滅する。

**「所有者が『事前入力の回答を許可』を有効にしていないと不可能」と一度結論づけたが、これは誤り。**
Microsoft のドキュメントは所有者が UI からリンクを作る手順を説明したもので、
回答者側が URL を組み立てられないことを意味しない。
**既存の下書きが上書きされた**という利用者の指摘が動かぬ証拠で、実機の観測を優先すべきだった。

したがって `src/core/prefill.js` は次を守る。

- 設問順（`order` 昇順）に並べる
- **値が空でもパラメータを出す**（穴を空けない）
- ファイル欄（16番）に達したら打ち切る。それ以降は届かないので載せない
- URL 超過時は**末尾から**削る。途中を抜くと以降が全部死ぬので、
  「重要度の低いものを抜く」方式は**この仕様のもとでは有害**だった（一度実装して撤回）
- 綴りは素の設問ID1通り

実測 1,409 文字で15問すべて収まる。

#### ブックマークレットから値を追い出した（2026-08-25）

以前はロジックと値を1本に固めていたため、**活動情報を変えるたびに登録し直しが必要**だった。
毎回内容が変わるツールでこれは致命的で、しかも氏名・メール・学籍番号がコードに焼き込まれるので
人に渡すと個人情報が漏れる。

いまはブックマークレットが**ロジックだけ**（26,919文字・不変）で、
値と設問マッピングは**リンクのハッシュ `#gsh=<base64url>`** で渡す。
ハッシュはサーバに送られないので長さ制限がない。設問マッピングも一緒に渡すので、
**大学がフォームを変えてもブックマークレットは無傷**（ツール側を更新するだけ）。

filler は `location.hash` → クリップボード → 貼り付け欄 の順に値を探し、
**どの経路で受け取ったかを結果画面に必ず出す**。

#### 実機で分かった制約（2026-08-24）

事前入力リンクを本番で試したところ、**設問1〜3（テキスト3問）だけ入り、4以降が全部空**になった。

原因は「**設問IDの綴りが未確定だったので2通りを両方送っていた**」こと。
これでパラメータ数もURL長も倍になり、二重に失敗していた。

- URL長: **2,641文字**（片方だけなら 1,374文字）→ こちらの上限判定で項目が脱落
- パラメータ数: 1問につき2個 → **Q1〜Q3 でちょうど6個**。そこから先が Forms 側で無視された

「最初の不明なパラメータで停止する」説は観測と合わない。その場合、
正しい綴りが素の `qid` なら Q1 だけ、`r` 前置なら何も入らないはずで、どちらも矛盾する。
**Forms 側にパラメータ数（かクエリ長）の上限がある**と考えるのが自然。

対策:
- `prefillPrefix` を `form-map.json` に持たせ、**綴りは必ず1通り**にした
- 綴りは実機でしか判定できないので、アプリ内に A案／B案 の判定リンクを置き、
  効いたほうを利用者が選んで保存できるようにした
- 落とす順番を「長い順」から `prefillPriority` の**低い順**に変えた。
  以前は加入制度（申請の本質）が真っ先に落ちるという筋の悪い動きだった
- `prefillMaxParams` で件数上限も設定できるようにした

`verify-bundle.mjs` が「`rr…` が混ざらないこと」「本番相当の全14問が上限内に収まること」
「上限が厳しいときに落ちるのが長い自由記述で、加入制度と申請先は死守されること」を検査する。

#### URL 長

日英併記の選択肢と自由記述を全部載せると 2,300〜3,000 文字になりうる。IIS 系のクエリ長上限が
2048 バイトのことがあり、超えると 404/414 になる。`MAX_URL` を 1900 にして、
超える場合は長い項目から自動で落とす（落とした項目は UI に出す）。実測で上限を叩いたら調整する。

### ファイルの自動添付（未実装・Phase 2）

`new DataTransfer()` で `FileList` を合成して `input.files` に代入し、
ネイティブ `change` を発火する手法は Chromium 系で有効。
Forms のアップローダは受け取ってから自前で OneDrive へ POST するだけなので、
認証やトークンを偽装する必要はない。

ただし、
- アップロード欄に**本物の `<input type="file">` があるか未確認**（`probe.js` が調べる）
- ドロップゾーン方式だった場合は `drop` イベントに `DataTransfer` を積む方式になる
- Fluent UI のラッパが DOM イベントを見ていない実装だと、どちらも通らない

そして根本的な制約として、**ローカル HTML ツールと forms.cloud.microsoft は
オリジンが違うので、ツール側から生成ファイルをフォームに渡す経路がない。**
自動添付をやるならユーザースクリプトか拡張が前提になる。

現状の割り切り: 名簿をダウンロードして手で添付する（1操作）。
元々の痛点は「同じ値の大量コピペ」であって添付ではないので、優先度は低い。

## 2.5 フォーム記入エンジンの設計（`src/form/filler.js`）

### 設問の特定は3段構え

1. **設問ID** — `document.getElementById('QuestionId_' + qid)` → `closest('[data-automation-id="questionItem"]')`。
   設問を作り直さない限り不変なので、並び順が変わっても文言が変わっても当たる。**これが本命**
2. **見出しの正規化一致** — NFKC → 空白除去 → 先頭連番除去 → 型サフィックス除去。
   **複数当たったら黙って先頭を採らずに失敗させる**
3. **並び順** — 設問数が `expectedCount` と一致し、**かつ見出しの先頭連番が期待値と一致する**
   ときだけ許可。大学が手で打っている `1.` `2.` … がチェックサムとして効く

どの段でも決まらなければ**触らずに警告する**。旧版の一番の問題は、外れたことに気付けなかったこと。

### 15.活動場所 と 14.活動場所（国内/海外）の衝突

正規化後の `活動場所` は `活動場所(国内/海外)…` に**包含される**。
この2問は `exactOnly: true` を立てて部分一致を禁止している。

（余談だが、この検証テストを書くときに `label.includes('箇所名')` として
 8.活動主管箇所名 を取り違えた。まったく同じ罠を自分で踏んだので、実在の危険。）

### 種別ごとの操作

| 種別 | やり方 |
|---|---|
| text / textarea | ネイティブ setter で value を設定 → input/change/blur。React に伝えるための定石 |
| radio | 選択肢の**完全一致**でクリック → `aria-checked` で検証 |
| dropdown | 開く → body 直下のポータルから option を探す → クリック → **閉じたことと表示を検証** |
| date | `yyyy/MM/dd` で入力 → **読み戻して数字の集合で照合** → 受理されなければ**空に戻して**警告 |
| file | 触らない |

### 記入順と再解決

**選択系（4/5/8/14）を先に、テキスト系を後に。** 選択で DOM が差し替わるため、
**毎回 `questionNodes()` を取り直す**。保持した参照を使い回すと古いノードを掴む。

### 条件付き設問（9番）

8番の**実際に入っている値を読み戻して**判定する。設定値では判定しない。
「8番の選択に失敗したのに9番だけ埋まる」が最悪の組み合わせなので。
条件を満たさないときは触らないが、**人が入れた値が残っていたら警告する**
（旧版がここに責任者名を書き込んでいたため、消し忘れが残っている可能性がある）。

### 報告は件数ではなく中身

完了バナーは「N項目入力しました」ではなく「**設問見出し → 実際に入った値**」の一覧。
今回のズレに誰も気付かなかったのは、結果を見せていなかったから。

## 3. 設計上の判断

### なぜ単一 HTML なのか

依頼の目的は「めんどくさがりな数人が実際に申請するようになること」。
**導入で1人でも脱落したら負け**なので、「ダブルクリックで開く」以外の手順を作らない。

Tampermonkey 版（自動添付ができる）と Chrome 拡張版も検討したが、
拡張のインストールは明確な脱落ポイント。まず確実に動くものを配り、
「もっと楽にしたい」の声が出てから Phase 2 に進む。

`file://` で ES モジュールは CORS で読めないので、スクリプトは
**クラシックスクリプトとして連結**している（`type="module"` にしてはいけない）。

### なぜ個人設定と団体設定を分けているのか

既存ブックマークレットをそのまま配ると、**全員が依頼者本人の名前とメールで申請する**。
実害が出る事故なので、

- `personal` が未設定なら名簿作成をロックする
- 「団体配布用」エクスポートには `personal` を**物理的に含めない**

の2段で防いでいる。

### なぜ設問マッピングを JSON に切り出しているのか

大学は年度替わりでフォームを更新しうる。`src/form/form-map.json` を分離してあるので、
**調査ブックマークレットを再実行して JSON を差し替えるだけで直る**（コードを触らなくてよい）。
アプリ内の「設問マッピングを更新する」から取り込める。

### マッチ失敗時に黙って進まない理由

インデックス依存の一番怖い壊れ方は「ズレたことに気付かないまま送信される」こと。
メールアドレス欄に氏名が入ったまま出す、のような事故が起きる。
`filler.js` はマッチ0件・複数件のとき必ず画面に警告を出す。

## 4.5 外部の挙動を確かめるときの手順

Microsoft Forms のような**手元で読めない相手**の挙動を調べるときは、必ずこの手順で行う。
これを守らずに「仮説 → 修正を出す → 試してもらう → 外れる」を3回繰り返した
（経緯は [事前入力の調査.md](事前入力の調査.md)）。

1. **1テストにつき新しい InPrivate ウィンドウ。** 終わったら閉じる。
   キャッシュ・下書き・前回の状態が混ざると、観測がすべて無意味になる。
   実際 Forms には「最初に開いた事前入力URLが効き続ける」というキャッシュ問題の報告がある
2. **1テストで1変数だけ動かす**
3. **観測は機械で取る。** `dist/読み取りブックマークレット.txt` を使い、目視で数えない。
   17問をスクロールしながら数えるのは間違えるし、こちらも検証しようがない
4. **送信しない。** テスト値はすべて `ZZ` 始まりにする
5. **複数の仮説を一度に潰せる形で実験をまとめて渡す。** 1往復1仮説だと収束しない。
   `node tools/make-experiment.mjs` が切り分け用のURLをまとめて生成する
6. **確認できていないことを断定しない。** 未検証の機能を既定の導線にしない。
   `verify-bundle.mjs` の「未検証の機能を主導線にしていないか」がこれを機械的に見張る

### 検査そのものが機能しているかを必ず確かめる

この件で作った検査は、最初**素通りする無意味なもの**だった。
「`N項目が入ります` と書いていないか」を数字で探したが、実際のコードは
`r.included.length + ' 項目が入ります'` と変数から組み立てていたので引っかからなかった。

**わざと壊した状態で検査が落ちることを毎回確かめる。**
`verify-probe.mjs` の `[4c]`、`verify-lint.mjs` の自己テストが同じ考え方。

## 5. 検証の考え方

`tools/` に4本ある。**名簿生成を触ったら全部通すこと。**

| スクリプト | 見ているもの |
|---|---|
| `verify-roster.mjs` | 触っていない zip エントリがバイト等価か、シート構造が不変か、値と型が正しいか |
| `verify-excel.ps1` | **Excel 本体が修復ダイアログなしで開けるか。** ここまで通って初めて「動いた」と言える |
| `verify-bundle.mjs` | 配布物の構文、埋め込みテンプレの一致、ID の整合、事前入力 URL の組み立て、CSP 適合 |
| `verify-browser.mjs` | Edge ヘッドレスで実際に動かす。`file://` で localStorage と CompressionStream が使えるか |
| `verify-probe.mjs` | **模擬フォーム**（`tools/mock-form.mjs`）に対して調査ブックマークレットを実際に走らせる |
| `verify-lint.mjs` | 構文チェックを通ってしまう書き間違いを探す（下記） |

### 構文チェックを通り抜けたバグ（`verify-lint.mjs` を作った理由）

`var備考 = findIdx('備考');` とスペースを入れ忘れて書いた。**`var備考` 全体が1つの識別子**として
解釈されるため構文としては正しく、`node --check` も `new vm.Script()` も通る。
strict mode の実行時に「未宣言変数への代入」で初めて ReferenceError になり、**本番フォームで踏んだ**。

日本語の識別子はキーワードとの境目が目で見えないので、機械的に潰すしかない。
`verify-lint.mjs` がキーワード直後に非 ASCII が続く箇所を探す。

注意点2つ:
- **`\b` は使えない。** JS の `\b` は「単語文字と非単語文字の境目」なので、`var` の直後が
  日本語だと期待どおりに働かず、最初に書いた走査は取りこぼした。`(?:^|[^A-Za-z0-9_$])` で明示する。
- **走査スクリプト自身の自己テストを入れてある。** 既知の書き間違いを検出できるかを毎回確かめる。
  スキャナが壊れると「該当なし」が嘘になり、壊れたことに気付けないため。

### テストしていない経路を残さない

このバグを踏んだ直接の原因は、`buildPrefillTestUrl()` が**一度もテストされていなかった**こと。
模擬フォームは `file://` で `?id=` が無いため、関数の手前で return していた。
`file://` URL にもクエリは付けられる（`file:///…/mock.html?id=TESTFORMID123`）ので、
今はそれで本番同様に走らせている。

あわせて、事前入力 URL の組み立ては独立した `try/catch` で囲んである。
**おまけの処理の失敗で、苦労して集めた第1段の結果まで巻き添えで失わない**ようにするため
（実際に最初はそうなって、ユーザーにはエラーだけが表示された）。

### 模擬フォームについて

本物のフォームは組織限定なうえ、うっかり送信する危険もある。そこで実測データから
Forms を模した HTML を組み立てて（`tools/mock-form.mjs`）、それを相手に検証する。
再現しているのは、設問IDの付き方、見出しの形（連番＋タイトル＋種別の読み上げ文言）、
ドロップダウンが閉じている間は選択肢が DOM に無く開くと body 直下にポータルされること、
隠れた `<input type="file">` の構成。

**「設問を1つ挿入したらどうなるか」のような、本物では試せない実験ができる**のが利点で、
今回のズレのバグはこれで回帰テストにしてある。フォームの実測結果が更新されたら
`tools/fixtures/probe-*.json` を差し替える。

最後の砦は**実提出**。1件だけ実際に出してもらい、大学側で受理されるかを確認する。
XML が正しいことと、大学の Power Automate が通ることは別の話。
